# Static and capture-based reverse engineering (PSP2i)

Tools in `.claude/skills/psp2i-static-re/scripts/` (run from the repo root with `python -I`, as the
generated code and captures are data, not code). Results go in
`port/docs/ADDRESS_MAP.md` (source and status for each address), as the
`vr-probe` skill says. `vr-probe` is the live side (F8, memory watches);
this skill is the code and capture side; `psp2i-hook-re` is the run-time
side (hook what you find here, count and override its decisions). Use them
together.

## The generated code is the disassembly

`port/gen/recomp_funcs.c` (~200 MB, generated by the `psp2i-build-run`
skill, git-ignored) has one `static void psp_body_XXXXXXXX(...)` per game
function, and every original MIPS instruction as a comment:
`/* 08AFCE90  addiu  $sp, $sp, -48 */`. Calls are `jal 0x...` comments.

| Question | Command |
|---|---|
| What does function X do? | `python -I .claude/skills/psp2i-static-re/scripts/disasm.py 08AFCE90` (`--all` for the whole body) |
| Who calls X? | `python -I .claude/skills/psp2i-static-re/scripts/callers.py 08D7D63C` |
| Who reads or writes globals in a range? | `python -I .claude/skills/psp2i-static-re/scripts/global_refs.py 08FA97A0 08FA97E0` |
| The local player's skeleton (nodes, parents, arm / leg chains)? | Run a dev build with `PSP2I_SKEL=FILE` (port/vr/vr_body.c: the player's model, node matrices twice a second, skeleton records once), then `python -I .claude/skills/psp2i-static-re/scripts/skeleton.py FILE` |
| Which player-object field follows play (facing, a button's state)? | Run a dev build with `PSP2I_PL_TRACE=FILE` (one record per game frame: pad as sent, headings, 4 KB of the local player, 512 bytes of the camera), then `python -I .claude/skills/psp2i-static-re/scripts/pltrace.py FILE facing` (fields that follow the walk direction), `changes` (button presses), `dump OFF` |

Tips:
- Globals are `lui $r, 0x8FB` + offset: `0x08FB0000 - 26720 = 0x08FA97A0`.
  `global_refs.py` resolves these; register-relative struct fields (camera
  `+0xFC`) it can't, so search the callers of a known accessor instead.
- Float constants come from `.rodata` (`lui $v0, 0x8E0; lwc1 $f0, -5332($v0)`),
  not from immediates, so searching for `lui 0x4370` (240.0) finds nothing.
- Arguments: `$a0..$a3`, then `$t0..$t3`; floats in `$f12..$f15`. In a host
  hook, `psp_cpu.r[4..7]` are `$a0..$a3` and `psp_cpu.r[12]` is `$t0`.
- A hook point must be listed in `port/hooks.txt`, then regenerate `gen/`
  (`psp2i-build-run` step 1) and register it with `psp_hook_set` in the host.
  Unregistered, the original runs unchanged.

## GE frame dumps (what the game draws)

F12 in a development build (or `--ge-dump VBLANK`) writes
`port/build/Release/dumps/draws_<vblank>.txt` (every draw: target, state,
vertices with screen and clip coordinates, the matrices when they change)
and `frame_<vblank>.ppm`.

- `python -I .claude/skills/psp2i-static-re/scripts/ge_frame.py seq DUMP` gives the frame's passes.
  For PSP2i: the 3D scene into `0x0CC000`, orthographic bloom passes,
  a second (depth) clear of `0x0CC000`, the HUD pass, then one through-mode
  copy to the display buffer `0x000000`.
- `python -I .claude/skills/psp2i-static-re/scripts/ge_frame.py hud DUMP` lists the HUD pass. Its draws
  are flat perspective sheets, and clip w is the layer: menus 3-70, field
  HUD 84-85.9, world labels 86-88, the minimap frame 86.9-87, and the
  minimap's 3D map ~2390 (with a small scissor).
- Ask the user for F12 at the moment that matters ("with the start menu
  open", "with names on screen"), with a windowed `--no-vr` run. Convert
  the `.ppm` to PNG with PIL and look at it alongside the list.

## VR captures (what the headset got)

In a development build with VR stereo on: **gamepad L3 held a second**
or **left grip + left stick click** on the VR controllers (use these in the
headset: F11 rarely reaches the game window then), **F11** in the game
window, or
`PSP2I_VR_SHOT_EVERY=N` (seconds) in the environment, writes to the capture
dir (`--capture-dir`, default `captures/`):
- `vrshot_<vblank>_L.ppm` / `_R.ppm`: both eye pictures, exactly as sent
  to the headset (that frame goes through the CPU instead of the shared
  texture);
- `vrshot_<vblank>.txt`: head pose and eye offsets, the HUD frame
  (yaw/pitch, following or still), the VR settings, the game's view
  matrix, and psprecomp's trace of one frame (`psp_gpu_stereo_trace`):
  - the latched eye matrices;
  - each draw that isn't a moved 3D scene draw: what the eyes did
    (`same`, `hud`, `shrink`), its clip w, menu/follow, target;
  - the left eye's screen box and scissor before and after.

`python -I .claude/skills/psp2i-static-re/scripts/vrshot.py CAPTURE_DIR` makes `vrshot_<vblank>.png`
(left | right) and summarizes each report (`--draws` for every draw). Read
the PNGs with the Read tool. For a headset complaint, run the game with
`PSP2I_VR_SHOT_EVERY=10` before asking the user to describe it again.

## Writing it down

Every address found goes in `ADDRESS_MAP.md` with how it was found
(disassembly, dump, watch, capture) and its status. Decisions that follow
go in `VR_PLAN.md`, the session's results in `VR_PROGRESS.md`.
